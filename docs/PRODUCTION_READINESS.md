# Ambry — Production Readiness Review

> **App:** Ambry (formerly the working name "Keepsake"), the serverless Immich + Telegram Android app in `../keepsake/mobile/`.
> **Date:** 2026-11-22. **Device:** Realme RMX3785, Android 15. **Library under test:** 576 items (399 photos, 177 videos, 11.35 GB) backed up from the phone's Camera album.
> **Builds on:** [PHASE4_8_LIBRARY_LOG.md](PHASE4_8_LIBRARY_LOG.md).

---

## 1. Verdict

**Ready for your own daily use and for a small closed beta. Not yet ready for a public Play Store launch.**

The core promise works end to end on a real phone. Photos and videos back up to your own Telegram, encrypted or not (your choice). They come back byte-identical, stream, show in all four screens, and survive deletion from the phone. What stops a public launch is mostly paperwork and a few safety rails, not the core: the final app ID and signing key, AGPL source publication, a privacy policy, the untested new-phone restore, and a guard against two phones writing one vault (§5).

## 2. Name and logo

| | |
|---|---|
| **Name** | **Ambry**: an old English word for a small cabinet built into a wall to keep precious things. It is short, easy to say, and sounds like *amber*, which preserves things forever. |
| **Why not "Keepsake"** | One letter away from **Keepsafe**, a photo-vault app with 50M+ downloads on Google Play, in the same category, which is a real trademark-confusion risk. "Everkeep" is also already taken by a memories app. No photo app named Ambry turned up. |
| **Logo** | A sunrise seen through an arched alcove: a cream arch with a thin frame, an amber sun rising behind two hills, on a warm amber tile. Works as a full-colour adaptive icon, a single-colour themed icon (Android 13+) and a notification icon. |
| **Files** | Master: `keepsake/branding/ambry-logo.svg`. Play Store icon: `keepsake/branding/ambry-play-512.png`. Every size is regenerated by `python keepsake/branding/generate_ambry_logo.py` (standard library only). |
| **Brand colour** | Amber `#B8540F` (light theme) / `#FDB44B` (dark theme) replaces Immich's indigo as the default theme colour. |

Still to do before launch: a trademark search in your target countries (India, US, EU) for "Ambry" in class 9 (software).

## 4. Bugs found and fixed in this pass

| # | Problem | Impact | Fix |
|---|---|---|---|
| 1 | **Albums tab did nothing**: creating an album or "Add to album" called the Immich server | One of the four main screens unusable | Albums now live in the on-device index (create, rename, description, cover, sort order, add/remove photos, delete). They are synced to the screens like photos and saved in the encrypted index backups, so they come back on a new phone |
| 2 | Index paging could **skip changes** when 500+ rows shared one change number | After a new-phone restore (which renumbers every row) part of the library could stay invisible | Every row now gets its own change number; existing indexes are renumbered once on upgrade |
| 3 | **102 videos shown at latitude 0, longitude 0** on the map (in the ocean off West Africa) | Wrong map; misleading Places | Cameras write `+00.0000+000.0000` when they have no GPS fix. Treated as "no location" when reading files and when syncing (one-time re-sync fixed the existing 102) |
| 4 | Search **Camera** filter lists were empty | Filter unusable | Make/model (and place) suggestions now come from the phone's own database |
| 5 | **"Move to locked folder"** was offered | The locked folder needs an Immich server PIN and has no page here, and the action also deletes the phone copy, so photos would vanish from view | Hidden |
| 6 | Server-only actions offered in the viewer: Cast, **Open in browser**, View similar photos, Set as profile picture, share links, likes, stacks | Broken buttons; "Open in browser" would also have written the private media-server address into the browser history | Hidden |
| 7 | People and Location search filters always empty; "Shared with me / My albums" album filters meaningless; "What's new" showed Immich's release notes | Looked broken | Hidden |
| 8 | Downloads saved to `DCIM/Immich` | Wrong brand in the user's gallery | `DCIM/Ambry` |
| 9 | 19 English messages (delete warnings, empty trash, upload button, battery hint…) said "Immich" / "Immich server" | Wrong and confusing ("still available on the Immich server") | Reworded to "Ambry" / "your Telegram vault" |
| 10 | Android permissions: background location, location foreground service, audio | Background location triggers a special Google Play review and was unused | Removed (foreground location kept for the map's "my location" button) |
| 11 | Network: plain HTTP allowed to any host, user-installed CAs trusted | Wider attack surface than needed | Plain HTTP only to `127.0.0.1`/`localhost` (the app's own media server); only system CAs |
| 12 | **Release build failed** at the R8 step ("optimized resource shrinking requires non-final IDs") | No production build possible | `android.nonFinalResIds=true`; explicit R8 keep rule for the TDLib JNI bridge |
| 13 | App version was Immich's `3.4.0-rc.0`, shown as "Ambry v3.4.0" | Confusing | `1.0.0+1` |
| 14 | Synced albums never got new photos while the app was open | Immich adds them when its **server** sends an "upload ready" websocket message; Ambry has none | Albums are brought up to date at the end of every in-app backup run |
| 15 | The app still asked the Immich server for the user profile (404 in the log) and offered a profile-picture upload | Errors in the log; a broken button | Profile read from the phone; avatar upload hidden |
| 16 | Settings offered server-only options: custom proxy headers, SSL client certificate, "Force original video" | Did nothing | Hidden |
| 17 | Free up space and delete messages said "server" ("Your copies on the server remain safe") | Wrong | "your Telegram vault" / "Ambry's trash" |
| 18 | Empty albums appeared for every folder picked for backup | Expected with **Sync albums** on (it is on in your app); empty ones fill on the next backup run | Behaviour kept; two empty test albums deleted |

## 5. Blockers before a public release

| # | Blocker | Why it matters | What to do |
|---|---|---|---|
| 1 | **Final application ID and signing key** | The ID (`app.keepsake.photos` today) and the signing key can never change after the first Play upload | Pick the ID (for example `app.ambry.photos` or a domain you own), create an upload key, enrol in Play App Signing. Changing the ID on your phone makes a new app: sign in to Telegram again and restore the vault (this doubles as the new-phone restore test) |
| 2 | **AGPL-3.0 obligations** | Immich's mobile code is AGPL-3.0. Distributing Ambry means offering its complete source under the same licence | ✅ Done in code: `keepsake/LICENSE` (AGPL-3.0 text), About shows "modified version of the Immich mobile app" and a **Source code** link to `github.com/CypherNinjaa/free-storage`. **Still to do:** make that repository public before release |
| 3 | **Telegram API terms** | Ambry uses your own api_id/api_hash; users sign in with their own (dedicated) account | Register the production app at my.telegram.org under the Ambry name, follow the API terms (no "Telegram" in the app name, no impersonation, privacy policy), and tell users plainly to use a dedicated account. Very large uploads can hit flood limits; Ambry already waits and retries |
| 4 | **Privacy policy + Play Data safety form** | Required for apps that read photos, location metadata and a phone number | ✅ Published: <https://github.com/CypherNinjaa/free-storage/blob/main/docs/PRIVACY_POLICY.md> (also linked in the app: account sheet → Privacy). Data safety answers: [PLAY_RELEASE.md](PLAY_RELEASE.md) §3 |
| 5 | **New-phone restore never run on a device** | Restore is the whole safety net | Run it once end to end (see blocker 1) before inviting testers |
| 6 | **One phone per vault** | Two phones using the same vault at once could overwrite each other's albums and edits | ✅ Done: only the active phone writes; a restore makes the new phone active; the old phone shows "Backups paused" with "Use this phone" |
| 7 | **Files over 1.95 GiB are refused** | Long 4K videos will not back up | Split large files into parts (Telegram's limit is 2 GB per file, 4 GB with Premium) |
| 8 | **Background backup on Realme/ColorOS (and similar)** | The OS freezes the app in the background unless "Allow background activity" is on | ✅ Verified working once allowed; the Backup screen warns with an "Open app settings" button while it is off |
| 9 | **Publish as an App Bundle** | The universal APK is 179 MB because it carries TDLib for three CPU types | `flutter build appbundle --release` (see [PLAY_RELEASE.md](PLAY_RELEASE.md)); Play then delivers only the phone's own CPU type |

## 7. Security review

| Area | Status |
|---|---|
| Encryption at rest in Telegram | On by default: AES-256-GCM per file with its own key, keys wrapped by the vault key (Argon2id from the passphrase; 24-word recovery kit). With encryption off, new files are stored as the original file and anyone with access to the Telegram account (and Telegram) can see them; captions, albums and the index stay encrypted |
| Vault key on the phone | Wrapped with an Android Keystore key; never written in plain form |
| Telegram session | TDLib database encrypted with a device-bound key; `allowBackup="false"`, so it is not copied to Google Drive |
| Media server | Loopback only (`127.0.0.1:47819`), random per-install path token, plain HTTP allowed only to loopback by the network security config, 404 without the token |
| Thumbnails on the phone | Encrypted with the vault's thumbnail key |
| Logs | Tokens, keys and captions are never logged |
| Permissions | Photos/videos (read), media location, notifications, manage media, foreground location (map button only); no background location |
| Open item | No crash reporting. Play Console vitals cover crashes only after release |
